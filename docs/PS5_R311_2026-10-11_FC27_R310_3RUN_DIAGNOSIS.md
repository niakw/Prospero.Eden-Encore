## Actual failure order, second run: emulator crash is downstream

In `/data/prosperoeden/user/log/eden_log.txt`:
1. `[1133.219] HW.Memory Unmapped Write32 @ 0x0`.
2. `[1133.219] nvmap.cpp:141 ASSERT LockForMapDeviceAddressSpace(...).IsSuccess()` fails.
3. `[1133.225] guest PANIC, error D401`.
4. Further writes/reads to unmapped address 0 and a non-mapped `0x12db200000` region.
5. `[1158.851] guest Job0: Cannot execute instruction at unmapped address 0x0`.

The last NULL instruction fetch is NOT proof that JIT executable alias mapping caused the
crash; the first direct evidence is a guest GPU nvmap page-table lock failure / invalid
CPU address mapping. Another third-run game-side user-space PANIC `0x1A80A` was
also logged near the end; do not silently equate with the second-run failure.

### Narrow R311 fix

`headless/backports/eden-ps5-nvmap-alloc-rollback.patch` (PS5_NATIVE only):
- Reject `nvmap::IocAlloc` for guest CPU address zero instead of pretending
  GPU backing exists when the pinned Eden core itself calls it unimplemented.
- When the guest page-table device-lock fails after `Handle::Alloc`, return
  `NvResult::BadValue`, reset `allocated=false` and clear the stored
  `address` under the handle mutex. **Do not call device UNLOCK on an
  unsuccessful LOCK.**
- Leave successful lock, texture/buffer cache ownership, guest write/read
  semantics, and non-PS5 nvmap logic untouched.

This prevents a false-success handle and possible later use of unmapped memory; it does
NOT implement the unsupported guest address-zero allocation mode and is NOT proof that
the game will survive or that its native memory request was valid.
A new pinned-Git-blob CI replay test and native compilation are required.

## Texture/HUD and pacing: demonstrated facts versus hypotheses

- `EDEN_VULKAN_TEXTURE_BUDGET` reported ~4.12 GB used late in run #1 against
  ~4.72 GB expected/~5.58 GB critical, `memory_short=0`. Cache budget pressure
  or active eviction alone is therefore **not demonstrated** as the cause of jersey
  corruption, HUD disappearance or turf pixelation.
- A single pinned Eden `format_lookup_table.cpp:276` assertion identified
  `texture format=0 srgb=false components={0 0 0 0}`, an invalid Switch TIC format.
  Treat as evidence of a malformed/stale descriptor, NOT proof all flicker has
  the same cause. Pixel-format RGBA8 fallback is not a real conversion for format 0.
- No `Render.Vulkan <Error>` appeared in the sampled `eden_log`; that
  does not establish that Vulkan draws were correct.
- Running actual settings in all sessions: native 1x, **Bilinear**, FXAA,
  output 1440p, 60-Hz panel (~59.94). FSR sharpness=50 setting is not active
  as a scaling filter when Bilinear is selected.
- Vulkan output at 1440p is subsequently bilinearly blitted to the fixed
  driver 4K swapchain. A second spatial upscale and FXAA may produce
  motion aliasing/soft turf on a 4K TV; texture-loading is not the only
  explanation and there is no proven per-frame texture-stream burst.
- The presenter receives near-exact 33.4 ms intervals for long runs; this
  corresponds to approximately two 60-Hz display intervals, NOT a general
  emulator-imposed CPU/GPU speed nerf. Source game target can itself be 30.
- GPU scheduler dispatch is a different `cadence`: R310 experimental
  `dispatch_mask=63` gives a handoff every 64 draws, **hard flush at
  512**. Max 512-draw handoff cadence could reduce handoffs but also grow
  latency, max batch occupancy and time to first GPU work. No empirical
  evidence supports changing to 512 globally. Keep R309 hard safety ceiling.
